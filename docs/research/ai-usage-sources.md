# AI usage source contract

**Status:** CURRENT. Source code inspected 2026-09-26 at [akitaonrails/ai-usagebar commit f78e266](https://github.com/akitaonrails/ai-usagebar/tree/f78e266be47edcc0f80abca0f47753ef760f4596); no authenticated provider request was made.

The named tool is **a third-party project**, not a repository in `mschulkind-oss`. Its [`usage --json` report](https://github.com/akitaonrails/ai-usagebar/blob/f78e266be47edcc0f80abca0f47753ef760f4596/src/report.rs#L560-L635) has schema version 1, ordered `entries` with provider IDs, status, staleness, timestamps and typed metrics. Use this as a subprocess data boundary: the UI receives normalized reports, not account credentials. The existing Waybar `text`/`tooltip` format is too compressed for detailed cards.

**Prototype contract:** accept a synthetic report file by default; `--live` runs `ai-usagebar usage --json` only when explicitly requested. This first view prefers the base `anthropic` entry and falls back to the first named `anthropic@<label>` account. Upstream can report several named accounts; showing all of them still needs a UI decision before claiming multi-account coverage. No authenticated data or account names enter committed fixtures. The report is the inventory: one tile per reported agent, in report order, so an agent the report omits has no tile while an explicitly selected missing provider remains visible as unavailable. Metric `headline` chooses whether the upstream considers a value or percentage primary; do not draw a balance as a quota bar. Upstream error and stale states remain visible.

## Pacing fields and limits

In the pinned upstream [pacing calculation](https://github.com/akitaonrails/ai-usagebar/blob/f78e266be47edcc0f80abca0f47753ef760f4596/src/pacing.rs#L75-L110), the point difference is **percentage of quota used minus percentage of the reset window elapsed**. A positive difference means spending faster than time passes (over pace); a negative difference means spending slower (under pace). It is not a count of requests or credits. The [report projection](https://github.com/akitaonrails/ai-usagebar/blob/f78e266be47edcc0f80abca0f47753ef760f4596/src/report.rs#L579-L611) includes `percent`, optional `window_secs` and `reset_at`, and a human-readable `detail` such as `Resets in 2d 22h · 57% elapsed · 1pts ahead`. It does **not** have a dedicated elapsed-percent or signed-point field. The prototype shows an elapsed-time marker for a quota either when it recognizes explicit `N% elapsed` detail (with consistent point direction) or when the report supplies both a valid reset timestamp and exact window length. Otherwise it keeps the unmodified detail and plain usage bar; a balance or a missing window must not get an invented pace estimate. Elapsed time is measured from the reset window and the clock, so a report that states the window keeps the marker on a stale reading; the source's own `N% elapsed` prose was computed when its observation was fetched and places no marker once the reading is stale. Only a current reading may carry the point-difference verdict at all, so stale data never looks like a current pace alert. Antigravity is a special case: its [upstream sections](https://github.com/akitaonrails/ai-usagebar/blob/f78e266be47edcc0f80abca0f47753ef760f4596/src/tui/panels.rs#L1043-L1077) suppress the prose point label but still project fixed five-hour and seven-day durations with reset timestamps. Its [vendor mapping](https://github.com/akitaonrails/ai-usagebar/blob/f78e266be47edcc0f80abca0f47753ef760f4596/src/antigravity/vendor.rs#L26-L49) has two **independent** Gemini and Claude/GPT OSS pools. Given both timestamp and duration, Sidescope may calculate elapsed fraction from the report at check time; if either is missing, invalid or out of the window, it omits the time mark. The check-time estimate can differ by a point near a boundary from an upstream value computed earlier. Do not infer a reset-window duration for pace calculations merely from a repeated `Gemini` label; repeated group names can still distinguish the first (5-hour) and second (weekly) label when both are present.

## Fast-moving — verify before building live distribution

Confirm upstream CLI version and report compatibility, provider terms and endpoint stability, authentication scope, rate limits, refresh cost and whether a local `ai-usagebar` binary exists. A read of source code establishes implementation, **not live reliability or provider authorization**. Keep this dependency optional until the seven-source report has been exercised on the owner's machine.

Muse Code moved under this app between two checks, so both readings are recorded. Upstream 1.35.0's [vendor-endpoints doc](https://github.com/akitaonrails/ai-usagebar/blob/main/docs/vendor-endpoints.md) evaluates Muse Code as *not implementable as a native vendor* — `api.meta.ai` serves inference only, the `dev.meta.ai` dashboard reads spend through a browser session, and the CLI's OAuth token reaches that same gateway — and offers a `[[custom]]` recipe that tallies the CLI's local session log through a loopback tally server. On the owner's host, 2026-10-13, the installed ai-usagebar reports Muse Code's own Session and Weekly windows instead: `ai-usagebar --vendor muse` prints `5h 2% · 7d 4%` with reset horizons and an account label under a **Muse Code Power Usage** plan. The card therefore draws Muse quotas, and falls back to reading reported spend and call rows only when a report carries no metrics. Confirm which shape the installed version produces rather than trusting either claim, and treat the plan prices and per-window prompt allowances as vendor marketing copy rather than an API surface.
